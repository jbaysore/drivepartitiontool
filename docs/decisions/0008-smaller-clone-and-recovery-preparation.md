# ADR 0008: smaller clone destinations and offline recovery preparation

Status: implemented and covered by pure/fake-platform tests; privileged VHD and boot verification remain open.

A smaller clone destination uses a compact layout with the source partition order/types preserved, new disk/partition identities, fixed-size raw utility partitions and file-image NTFS data/Windows partitions. Known allocation sizes give the preview estimate; complete snapshot logical sizes are checked again before erasure, including filesystem working space. Unknown/overlapping/unsupported extended-MBR layouts are refused. Spare space goes to the last imaged data partition while trailing recovery partitions remain after it.

Transfer images live in a new GUID folder on a **third local disk**, resolved through ancestor junctions to a volume GUID. Source/destination aliases, unknown/read-only/offline staging volumes and insufficient staging space are refused; development/test staging disks must also be virtual. Staging needs conservative uncompressed-image space. This requirement preserves the source and allows a destination that cannot hold both applied files and transfer images. DISM capture with integrity/verification/EA flags completes before target erasure. After layout recreation, raw writes occur offline, images are applied to formatted NTFS destinations, and layout/filesystem and boot-file creation are checked. Temporary letters, shadows, links and owned files are tracked for failure cleanup; unrelated staging files are never recursively deleted. Actual permissions, streams, hard links, reparse points and boot behavior still need VHD/VM tests.

The clone UI explains this path and staging requirement, resets typed confirmation when choices change, refuses an unreviewed plan and freezes choices during execution. The former unconditional smaller-disk refusal is replaced in implementation, not declared verified by the earlier large-destination VHD result. A dedicated three-VHD test is prepared and unrun.

Windows copy measures the available recovery image before erasing anything, reserves at least 1 GiB or image size plus 250 MiB of servicing space, and retains recovery immediately after Windows. UEFI uses at least 300 MiB for EFI, including 4K-native disks. GPT recovery attributes are prepared by a fixed, integer-only script scoped to the rechecked destination/recovery partition, followed by a no-default-letter check; BIOS uses recovery type 0x27. A readable recovery image is registered with an explicit offline `/target`.

Activation is prepared as a human-readable instruction file on the destination. It tells the owner to boot the copy with the source disconnected and then run `reagentc /enable` and `/info` inside that copied Windows. No host/source `/enable` command or automatic first-boot task is introduced. Missing images are reported as unregistered recovery space. Actual GPT attribute persistence, offline registration, activation and recovery startup remain elevated/VM evidence requirements.

Sources: [Microsoft partition sizing/layout](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/configure-uefigpt-based-hard-drive-partitions?view=windows-11), [GPT attribute bits](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/gpt), [offline registration and activation context](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/reagentc-command-line-options?view=windows-11).
